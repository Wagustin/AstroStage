## 2024-06-29 - Email HTML Injection & Info Leakage
**Vulnerability:** The API endpoint `api/subscribe.ts` was vulnerable to HTML Injection because it embedded the user-provided `email` directly into the HTML of the outgoing email without escaping. Additionally, it leaked internal server error messages to the client and trusted the `Host` header for generating the logo URL (Host Header Injection).
**Learning:** Even when sending emails, user input must be sanitized. Email clients render HTML, making them susceptible to injection attacks. Trusting user-provided headers like `Host` can lead to SSRF or phishing vectors in emails. Finally, exposing `error.message` to the client violates the "fail securely" principle.
**Prevention:** Always escape user input before embedding it in HTML. Never trust the `Host` header for constructing URLs sent in emails. Generic error messages should be returned for 500 errors.

## 2024-06-30 - Vercel API Input Validation & Unhandled TypeErrors
**Vulnerability:** The API endpoint `api/subscribe.ts` was susceptible to an unhandled `TypeError` (resulting in a 500 server crash) because it destructured `req.body` and assumed `email` was a string without verifying if `req.body` existed, was an object, or if `email` was correctly typed. This is a common issue with Vercel raw request objects.
**Learning:** Vercel serverless functions receive raw request objects where `req.body` might be missing or not in the expected format (e.g. string instead of object) depending on headers. Attempting to destructure properties or call methods on missing or incorrectly typed fields leads to server errors, creating a potential DoS vector.
**Prevention:** Always explicitly validate the existence and type of `req.body` (`if (!req.body || typeof req.body !== 'object')`) before attempting to destructure or access its properties. Further validate all extracted fields (e.g., `typeof email === 'string'`) before calling type-specific methods like `.includes()`.
